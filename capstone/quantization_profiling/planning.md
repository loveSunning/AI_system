更新日期：2026-10-19。已完成规划、文件骨架、ModelScope 下载脚本和并行环境检测脚本；P1-01 工具实现中，目标机验证及模型实验待执行。本文依据 [项目说明](README.md) 与 [W29–W52 计划](../../docs/learning-plan-w29-w52.md) 展开；不把计划日期经过、文件存在或阅读完成等同于实验通过。

## 1. 项目目标与范围

最终回答四个问题：Qwen3-8B 在本机能运行哪些负载；BF16 的时间和显存花在哪里；W4A16 在哪些条件下改善或恶化指标；这些变化伴随多少质量损失。

必做闭环是：固定环境和模型 → 冻结数据与评测规则 → BF16 基线 → nsys 定位阶段与 ncu 抽样热点 → AWQ 优先的 W4A16 对照 → 留出集质量回归 → 汇总、解释与复现。完成闭环后，再考虑扩大实验范围。

| 范围 | 本项目安排 |
| --- | --- |
| 模型与设备 | Qwen3-8B；RTX 4090D 单卡，用户给定约 20G 可用显存；仍需在目标机读取实际值，当前本地验证机不是目标实验机 |
| 服务框架 | 选定并锁定一个 vLLM 版本；读懂本项目所需的请求、调度、模型执行和量化 kernel 路径 |
| 基线与量化 | BF16 为主基线；AWQ/W4A16 为首选量化路径，记录真实激活 dtype、KV dtype 和 kernel |
| 性能诊断 | prefill/decode、CPU/调度/launch、权重与 KV 访问、热点 GEMM/attention；先抽样 3 个代表热点 |
| 质量 | 100 条固定留出任务、逐题判分；独立语料 PPL 选做 |
| 暂缓 | 多框架完整对比、训练/微调、自写量化 kernel、INT8/FP8 全矩阵、多卡和跨平台迁移；分别留给后续案例或选做 |

首轮已完成规划与空文件骨架。现阶段按用户要求实现 download_models.sh 与 collect_environment.py，并同步使用说明；其余 YAML、服务/评测脚本、真实数据和报告保持待实现。下载脚本尚未实际拉取权重，目标 4090D 机器待执行环境检测，不能据此标记 S0 完成。

## 2. 学习内容与依赖路径

| 顺序 | 要学的知识 | 对应实践 | 学会的判断标准 |
| --- | --- | --- | --- |
| L1 模型与请求 | decoder 推理、tokenizer、chat template、thinking、prefill/decode、GQA/KV cache | 从锁定 revision 读取模型配置，跟踪一个请求从文本到生成 token 的过程 | 能区分用户文本长度、最终输入 token 数、目标输出长度与实际输出长度 |
| L2 显存预算 | 权重、KV、激活、workspace、CUDA Graph、分配器预留 | 估算后对照加载和请求过程中的显存观测 | 能解释权重放得下而服务仍 OOM 的原因 |
| L3 性能测量 | 流式时间戳、TTFT/TPOT/吞吐、排队、分位数、预热、缓存与重复实验 | 建立 BF16 基线并保留逐请求记录 | 能复算指标，解释单请求速度与服务吞吐的差别 |
| L4 性能诊断 | nsys 时间线、NVTX/执行阶段、ncu、算术强度、带宽/算力/launch 限制 | 短输入和长输入代表负载的时间线与热点表 | 能用 trace 和计数器支持瓶颈判断，不凭 dtype 或单个 utilization 数字下结论 |
| L5 量化原理 | PTQ、W4A16、scale/zero point、group size、校准、AWQ 的激活感知权重量化 | 锁定工具链、检查权重元数据、验证实际调用的量化 kernel | 能解释 weight-only 量化、反量化开销及收益随负载变化的原因 |
| L6 质量与报告 | 数据隔离、固定判分、配对比较、百分点、小样本限制、证据链 | 100 条留出任务回归，汇总实验 ID 与失败样本 | 能说明“性能更好”是否同时满足质量目标及其适用边界 |

依赖关系：L1/L2 是数据准备和服务启动的前置；L3 的干净计时通过后再开展 L4；L5 复用 L3 的协议；L6 的数据与判分必须在查看量化结果之前冻结。

先复用仓库已有 GEMM、CUDA 和 Nsight 基础，按热点补知识。第一次闭环不要求通读整个 vLLM 源码，也不把完整学习新的框架作为前置。

## 4. 分阶段实施与验收

### S0：锁定环境和模型（P1-01）

要学：模型加载链路、运行时依赖、权重/KV 显存组成，以及驱动、CUDA runtime、PyTorch 和服务框架版本的区别。

后续操作顺序：

1. 选择实际支持目标 GPU、Qwen3-8B 和候选量化格式的 Linux 环境；Windows 可用于文档和结果分析，WSL2 路径须另记环境并先做支持验证。
2. 记录 OS/kernel、CPU/RAM、GPU 型号/数量/UUID/实际显存、驱动、CUDA toolkit/runtime、Python、PyTorch、vLLM、tokenizers/Transformers、Nsight 版本、包清单和仓库 commit/工作区状态。
3. 固定模型 ID 与不可变 revision；保存 tokenizer revision、模型 config、chat template 文本及 hash、生成参数和服务完整命令。不得用可变的 main 代替已锁定 revision。
4. 从真实 config 读取层数、attention/KV head 数、head_dim 和 dtype，估算可用上下文与并发。thinking 主对照组计划关闭，并验证服务端实际应用了该设置；开启 thinking 的实验另组记录。[Qwen3 模型卡](https://huggingface.co/Qwen/Qwen3-8B) 描述了开关及不同模式的生成建议。
5. 分别观测空闲设备、加载完成、预热后和正式负载阶段，形成估算与实测对照。

预算关系：总显存 ≈ 权重 + KV cache + 激活/workspace + Graph/运行时开销 + 分配器预留与余量。粗估 BF16 权重可用“参数量 × 2 bytes”；8B 级模型约 16GB（十进制），不代表整机需求。KV 理论 payload 可用“2 × 层数 × KV heads × head_dim × 每元素字节 × 所有在途序列的已缓存 token 总数”，另计分页、对齐和预分配开销，不硬编码其他模型的结构。

验收：环境可重建；所有关键版本、revision 和命令有记录；能解释至少一组目标负载的显存预算。模型/硬件不支持时先记阻塞与替代方案，不进入正式对比。

### S1：冻结请求、质量数据与测量协议（P1-02 / P1-05 前置）

要学：tokenizer 与模板如何改变输入长度、性能合成负载与质量任务的用途、数据泄漏及评测规则冻结。

1. 在 workloads.yaml 未来配置五组负载、并发、请求数、预热、轮数、请求顺序、种子、缓存策略和输出限制。
2. 生成可重复的请求，使用锁定 tokenizer 在最终模板渲染后核验输入 token 数；保存请求快照和 hash，避免客户端/服务端重复套模板。不能以字符数或模板前 token 数代替实际输入长度。
3. 计划每个配置单元先预热至少 5 个请求；正式每轮 100 个请求、至少 3 轮。该值是项目初始协议，启动前按预算冻结；若减少样本，必须披露样本数及 p95 不稳定的限制。
4. 准备 100 条有可判定答案的留出任务，并单独准备校准数据；记录来源、许可、样本 ID、去重方式、随机种子和文件 hash。可采用选择题、数值计算、字段抽取、结构化指令遵循各 25 条的初始分层方案。
5. 冻结判分规则、质量目标和性能/质量各自的生成参数。质量采用正常停止规则；性能若强制固定长度，其输出不用于质量判分。

验收：两种精度能重放完全相同的请求；输入 token 与预期匹配；质量集恰好 100 条、ID 唯一、有参考答案和固定判分器；校准与留出数据无已知交叉；协议在看结果前已记录。

### S2：建立 BF16 基线（P1-02）

要学：流式请求的计时边界、服务排队与 GPU 阶段的区别、稳定测量、并发与容量。

1. 先实现配置读取、环境采集和服务启动的最小路径；用一个短请求验证模型、模板、thinking、输入输出 token 和流式事件。
2. 从 128/128 × 并发 1 开始，验证记录字段和指标可复算，再运行其余四组负载。
3. 预热覆盖目标 shape，记录 JIT、模型加载和 Graph 捕获是否发生；将这些一次性成本从稳态测量中分开。
4. 每个配置测至少 3 轮，保存每轮 ID、逐请求数据、服务启动日志和显存采样；正式性能测试不开 profiler。
5. 并发 1 完成后尝试 8/16。遇到 OOM/超时/拒绝，保留失败；重启、缩短上下文或降低并发均作为新配置，不覆盖旧记录。

验收：五组必做负载均有成功记录或明确失败证据；共同可运行的 case 至少有 3 轮有效测量；代表请求可以复跑。若 BF16 最小 case 仍无法运行，则标记基线受阻，不能宣称完成 BF16/W4A16 性能对比。

### S3：从时间线定位到热点 kernel（P1-03）

要学：prefill/decode 的计算形态差异、CPU/GPU 间隙、访存与算力限制、profiler replay 的影响。

1. 从成功基线中选择短输入、长输入、较长输出的代表 case，例如 128/128、4096/256、1024/512；用最小稳定请求序列采集。
2. nsys 采集实际执行模型的 worker 进程，结合 runtime 标记或日志识别 prefill/decode；核验子进程覆盖，避免只抓到 HTTP 客户端或 API 进程。
3. 统计热点总耗时、调用次数、单次耗时和所在阶段，并观察 CPU 调度、同步、拷贝、kernel launch 与 GPU 空隙。阶段可能交错，GPU kernel 耗时之和不能直接等同于端到端延迟。
4. 选 3 个代表热点，用 ncu 按 kernel 名/launch 范围抽样；先看时长、DRAM/计算吞吐、occupancy、寄存器/shared memory 与 launch 规模，再按问题增加计数器。
5. 形成“观察 → trace/计数器证据 → 瓶颈假设 → 单变量验证方案”的链条。先解释至少一个热点，再决定是否额外优化；本项目不要求实现新 kernel。

验收：能在时间线上指认阶段，3 个热点均有可定位记录，至少一个瓶颈假设有证据支持。权限或 Graph/replay 限制导致采集失败时保留日志；若为诊断关闭 Graph，另记配置，不冒充正式性能结果。方法参考 [仓库 Nsight 手册](../../docs/profiling/nsight-tools.md) 与 [vLLM profiling 文档](https://docs.vllm.ai/en/stable/contributing/profiling/)。

### S4：运行 W4A16 并做配对比较（P1-04）

要学：AWQ 的校准与分组量化、权重格式和运行 kernel 的关系、反量化及不同 batch 下的开销。

1. 优先选 AWQ，核验 GPU、锁定 vLLM 版本、权重格式与 kernel 的兼容性。工具选择依据当时的官方支持；[vLLM AWQ 文档](https://docs.vllm.ai/en/stable/features/quantization/auto_awq/) 已提示 AutoAWQ 库弃用并转向 llm-compressor，不能把旧版安装教程直接当作新环境方案。
2. 在“自行量化”和“使用已量化权重”之间明确选一条主路径。自行量化需记录源模型 revision、工具版本、完整 recipe、校准集 hash/条数/长度/seed、group size、zero point 和跳过层；使用现成权重需记录仓库/revision、基础模型关联、量化配置和可获得的校准信息。
3. 现成权重若不能确认来源于相同基础 revision，标记为部署方案比较，不能将差异全部归因于量化。未知的校准信息如实记为未知，不补造。
4. 记录加载日志和实际 kernel/后端，区分权重位宽、激活 dtype、KV dtype。W4A16 不能推导出 KV 已量化，也不能保证激活一定是 BF16。
5. 在 BF16 共同可运行的配置上复用同一请求序列、缓存策略、并发和生成参数，完成至少 3 轮干净计时；再按需要采集量化热点解释变化。
6. 量化可独立增加上下文/并发做容量实验，但与公平配对结果分组。如果后端只支持 FP16 激活，保留 BF16 主基线并注明 dtype 变化；需要隔离量化影响时补 FP16 对照，不能悄悄改名为 BF16 对照。

验收：一条 W4A16 路径稳定生成；权重来源、量化参数和实际后端明确；共同负载的性能与质量协议一致。AWQ 不可用时可选锁定版本支持的 GPTQ/W4A16 替代，并如实命名配置/结果，不把 GPTQ 写进 awq.yaml 冒充 AWQ。方法和硬件支持以 [vLLM 量化文档](https://docs.vllm.ai/en/stable/features/quantization/) 及本机验证为准。

### S5：质量回归与失败样本分析（P1-05）

要学：配对样本、准确率差值、基础模型错误与量化新增错误、随机生成和小样本限制。

1. 在同一 100 条留出任务上分别运行 BF16 和 W4A16；使用相同 prompt、模板、thinking、生成参数、正常 EOS/stop 规则和预设种子。不以性能强制长度输出判质量。
2. 按冻结规则逐题判分：选择题核对选项；数值题使用预定数值格式/容差；字段抽取和结构化输出校验字段、类型与约束。归一化规则与容差在看结果前固定，不能事后放宽。
3. 保留原始输出、提取答案、参考答案、分数、错误类型和 finish reason。格式错误、截断及未答对按预定规则计错；基础设施失败单独统计，按预定策略重试，未完成 100 条时不宣布通过。
4. 总体准确率用同一分母 100，分任务报告正确数与分数；计算“量化准确率 − BF16 准确率”（百分点），列出 BF16 对/量化错和 BF16 错/量化对的配对变化。
5. 建议在首轮评测前将“准确率下降 ≤2 个百分点”锁为项目目标；这是计划目标，后续必须记录是否采用，不能看结果后改门槛。100 条中 1 条对应 1 个百分点，小样本通过不代表广泛任务无退化。

验收：两组各有 100 条有效评测结果；数据和判分器有指纹；总体/分项结果与逐题记录一致；结论明确区分通过、未通过和未完成。若未过线，保留原始结论，修改校准或配方后创建新实验；反复调参后需另备未参与调参的最终验证集。

### S6：报告、复现与项目讲述（P1-06）

要学：配对实验解释、局限表达、从结论追溯到原始证据。

1. 校验数据完整性，按精度、版本、硬件、workload、并发、缓存和后端分组生成汇总；保留失败配置，不合并不相容组。
2. 报告延迟、吞吐、显存和质量的取舍；区分同配置对照与不同容量方案、单 kernel 变化与端到端变化。无显著收益或变慢也是有效结果。
3. 以至少一个真实瓶颈展开解释，提供实验 ID、trace 位置、配置和后续可测的优化假设，不把所有 decode 都预判为 memory-bound。
4. 在另一环境或重建的干净环境复跑一个共同可运行的 BF16/W4A16 配对 case；记录差异。后续 W50 按总路线补另一环境复现；未完成的复现项必须明确保留。
5. 最后补经过实际验证的 README 命令，准备 5 分钟演示和 15 分钟讲述：问题、口径、证据、结果、失败与限制。

验收：每个性能数字和质量结论都能定位到原始记录；有人按文档能找到环境、模型、数据、启动与结果入口；未验证事项明确标注。达到 W32 核心交付条件后可用于首轮作品集，W50 的复现状态单列。

## 5. 固定实验矩阵与指标口径

### 5.1 工作负载与对照组

| workload ID | 最终输入 token / 目标输出 token | 主要观察问题 |
| --- | --- | --- |
| w128_o128 | 128 / 128 | 短请求基础开销与 decode |
| w1024_o128 | 1024 / 128 | 中等输入的常规对照 |
| w4096_o256 | 4096 / 256 | 更长 prefill、KV 与 decode |
| w8192_o128 | 8192 / 128 | 长上下文、容量边界与 TTFT |
| w1024_o512 | 1024 / 512 | 更长输出的 decode 和端到端成本 |

最小主矩阵为“2 种精度 × 5 组负载 × 并发 1 × 至少 3 轮”。每格记录成功、OOM、超时、拒绝或不可支持状态；失败不能填 0ms 或伪造吞吐。只有共同成功的格子才能计算配对收益。并发 8/16 是容量允许时的后续扩展，并发 32 选做。

先采用固定并发的 closed-loop 请求模式，记录客户端最大在途请求数与补发方式。开放到达率/QPS 实验属于扩展，必须单独标注请求率、队列与持续时间，不能与固定并发结果混在一起。

主对照尽量固定输出 token 数；是否忽略 EOS、如何限制长度须按锁定版本验证并记录。长度不一致时同时展示目标/实际 token、结束原因和分布，不直接把更早停止当作性能提升。最大上下文必须覆盖最终输入与输出预算，并核验模板和系统 token 已计入。

### 5.2 指标定义

| 指标 | 项目定义与边界 |
| --- | --- |
| TTFT（ms） | 客户端提交请求至收到首个有效生成 token/内容事件；排除空 role/header 事件，包含网络和服务排队；客户端并发槽等待另记 |
| TPOT（ms/token） | （末 token 接收时间 − 首 token 接收时间）/（实际输出 token 数 − 1）；输出少于 2 个 token 时为空值 |
| E2E（ms） | 请求提交至完成事件；与末 token 时间分开保留，包含完成通知等尾部开销 |
| 输出吞吐（token/s） | 测量窗口内成功请求的实际输出 token 总数 / 整轮墙钟时间；窗口从首个正式请求提交到最后一个正式请求结束或超时，不排除失败等待时间 |
| 请求吞吐与错误率 | 成功请求数 / 同一墙钟时间；失败数 / 全部正式请求数；错误按 OOM、超时、拒绝、解析失败等分类 |
| 显存 | 记录加载后和测量期的设备显存、峰值采样值、采样间隔；可获得时另记 worker 的 allocated/reserved；预分配 KV、设备占用与活跃张量显存不能混称 |
| 质量差值 | 100 ×（量化正确数/100 − BF16 正确数/100），单位为百分点；分项分母分别记录 |

流式 chunk 可能包含多个 token，接收时间不能冒充精确的逐 token GPU 时间。保存 chunk 时间、内容和服务 usage/实际 token 计数来源；无法得到精确逐 token 边界时，把客户端 TTFT/TPOT 标记为流式观测近似，不宣称获得精确 ITL。指标和可用参数参照 [vLLM benchmark 文档](https://docs.vllm.ai/en/stable/cli/bench/serve/)，自行实现后还需核对同版本行为。

每轮对逐请求 TTFT/TPOT/E2E 报告 p50/p95、有效样本数；汇总再报告各轮统计量的中位数和范围。分位数算法固定并记录；不能把三轮均值的 p95 当成请求级 p95。吞吐按轮展示并汇总，不取单请求 token/s 代替聚合吞吐。

### 5.3 控制变量

- 配对组固定基础 revision、tokenizer/模板、thinking、请求快照、生成参数、并发与调度设置；记录 attention backend、Graph、chunked prefill、KV dtype 和显存/KV 预算。量化必须改变的项显式列出。
- 主对照关闭 prefix caching，并验证状态；模型/JIT 预热后测量。若无法关闭缓存，则使用统一的独立前缀与重置规则并披露。冷启动成本、前缀缓存冷/热状态分别记录，不能只给某一精度缓存命中优势。
- 主对照固定同一 KV token 容量或可核验的共同调度预算；若运行时只能按显存比例分配，记录实际 KV blocks/token 容量并披露这一差异。充分利用量化释放显存的容量实验另列。
- 尽量交替运行 BF16/W4A16 配对批次；保留时间、温度/功耗、后台负载与波动信息。异常值只按事先约定规则标注，原始记录保留。
- Profiler 只服务于诊断，干净计时不挂 nsys/ncu；GPU 单 kernel 计时需要正确同步，客户端流式测量按请求边界进行，不逐 token 人工同步。

## 7. 数据、实验 ID 与证据保存约定

下面是字段设计，不是已生成的数据。单位用字段后缀标明，时间戳使用单调时钟做耗时计算，UTC/时区时间用于实验索引；无效指标写 null 并说明原因，不写 0。

实验 ID 建议形如“p1-日期时间-精度-workload-c并发-r轮次-唯一后缀”；原始记录只追加，同一请求用 (run_id, request_id) 去重校验。质量与 profiling 使用独立 run ID 并引用对应的性能配置。配置、数据或代码变更后创建新 run，不能覆盖旧结论。

未来生成产物统一放仓库忽略的 `out/quantization_profiling/<run_id>/`：包括环境/manifest、请求快照、服务日志、显存采样、质量逐题结果、CSV 和 trace。该目录按运行创建，环境采集可通过 --output 显式写入 JSON；可再生成项目级跨 run 的 baseline.csv、量化对照 CSV 和 quality.csv，保留原计划交付口径。小型原始性能记录可进入指定 data/performance.jsonl，报告引用 run ID 和 manifest。

大型权重与数据缓存放外部缓存/实验存储，不提交仓库。大型 trace 和日志若仅存在本机 out/ 并不足以支撑他人复现，正式交付时需另给可访问的归档位置、相对索引与 hash。报告中的截图不能替代原始证据。此处只约定保存规则，不生成这些产物。

## 9. 风险处理与停止条件

| 情况 | 处理方式与完成边界 |
| --- | --- |
| 显存不足 | 并发 1、短负载起步；记录 BF16 失败边界。降低上下文/并发另建配置；换卡独立分组；量化能运行不能替代 BF16 基线验收 |
| 量化格式/工具不兼容 | 先做单请求 smoke；查锁定版本支持并固定 recipe。必要时改用明确命名的 GPTQ/W4A16；不无限尝试多个量化库 |
| 自行量化资源不足 | 可先用可追溯的现成权重完成部署评测；标明校准/生成信息缺失，自行量化学习项单独延期 |
| 指标抖动 | 排查负载、温度/功耗、后台进程、JIT/Graph 和缓存状态；新采集另建 run，不删除原始异常记录 |
| Profiler 权限/进程覆盖问题 | 保存错误和当前覆盖范围，先完成干净基线；诊断项保持未完成，待条件满足后补采集 |
| 质量目标未通过 | 如实报告退化，分析配对错误与截断/模板/校准原因；调参后创建新实验并考虑新的最终验证集 |
| 到期仍未完成 | 优先保留环境、五组负载记录、最小共同对照、热点证据和质量回归；削减并发/INT8/FP8/PPL 选做，不以缩减样本或删失败掩盖缺口 |

首轮闭环达到报告和复现要求后停止扩展本项目，转入 P3 的服务调度学习。每个后续优化只围绕一个能用数据验证的问题，不预设量化必然加速或固定加速倍数。
